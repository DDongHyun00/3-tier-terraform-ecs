# DEC-25. 배포와 롤백 시간을 운영 환경에서 실제 배포로 쟀다

- 상태: 확정
- 날짜: 2026-10-28

## 배경

설계 때 정한 측정 항목은 "수동 대비 배포 소요 시간, 롤백 소요 시간"이었다. 그런데 예전 수동 배포 기록에는 롤링 2분 42초만 있고 빌드 시작 시각이 없어 전체 시간을 비교할 수 없었다. 배포 워크플로의 단계 요약 시각은 머지부터 러너 시작까지를 재지 않았고, 끝 시각에는 배포 액션의 확인 지연이 섞였다.

제약도 있었다. ECR 태그가 불변이라 잴 때마다 `app/**`가 바뀐 새 main 커밋이 필요했다. OIDC 신뢰 조건이 main 브랜치와 PR만 허용해서 실패 이미지도 main을 거쳐야 했다. 당시에는 환경이 운영 하나뿐이었고 실사용자가 없는 데모였다.

고려한 것:
- "수동 대비"라 빌드부터 안정화까지 전 구간을 같은 날 같은 조건으로 재야 표가 의미 있다.
- 롤백은 서킷 브레이커가 실제로 도는지와 그동안 사이트가 살아 있는지까지 보여야 한다.
- 운영 스택을 띄워 둔 시간이 곧 비용이라, 측정은 한 세션에 끝내고 바로 destroy한다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 수동 배포를 측정 당일 다시 잼 | 자동과 같은 조건으로 비교된다 | 약 15분 가동에 약 0.07 USD가 들고 ECR에 수동 이미지가 남는다 |
| 예전 수동 기록만 씀 | 추가 비용이 없다 | 빌드와 push 시간이 없어 비교가 안 된다 |
| 정상 배포를 `app/**` 변경 PR 머지로 2회 | 실제 배포 경로 그대로 잰다 | 측정용 커밋이 main에 남는다 |
| 정상 배포를 수동 실행(workflow_dispatch)으로 | 머지가 필요 없다 | 태그가 불변이라 1회만 되고 캐시가 다 맞아 짧게 나온다 |
| 실패 이미지를 코드 머지로 배포 | 워크플로의 실패 판정까지 검증한다 | main에 실패 커밋과 되돌림 커밋이 남는다 |
| 틀린 태스크 정의를 CLI로 등록 | 코드 이력이 깨끗하다 | 워크플로 판정을 못 보고 다음 배포가 틀린 설정을 물려받는다 |

## 결정

- 수동 배포를 같은 날 1회 다시 쟀다.
- 정상 배포는 PR 머지로 2회 쟀다. 하나는 되돌림 PR이고, 하나는 Java 주석 한 줄만 바꾼 PR이다.
- 실패 배포는 앱이 `ASSETS_BUCKET`을 읽게 바꾼 코드를 머지했다. 태스크 정의는 `S3_BUCKET`을 그대로 넣어서 운영에서만 기동에 실패한다.
- 순서는 수동 배포, 실패 배포와 롤백, 정상 배포 2회로 했다. 새 apply가 ECR 최신 이미지로 뜨기 때문에 정상 이미지가 마지막에 올라가야 했다.
- 배포 워크플로는 고치지 않고, ECS 기준과 워크플로 기준 두 값을 함께 적었다.
- 시각은 PR 머지 시각, 워크플로 단계 시각, ECR push 시각, ECS 서비스 이벤트, 앱 로그에서 뽑았다.

## 결과

- 시작부터 서비스 안정화까지 수동 5분 18초, 자동 5분 5초(캐시 적중), 자동 7분 38초(코드 변경)였다. ECS 롤링은 세 경우 모두 3분 남짓으로 같았다. 자동화로 줄어든 건 시간보다 손이 가는 일(명령 13개에서 머지 1번)이었다.
- 롤백은 실패 판정까지 4분 5초, 이전 버전 복귀까지 1분 14초, 합계 5분 19초였다. 그동안 liveness 응답 217회가 모두 200이었다.
- 워크플로는 롤백이 끝나고 8분 33초 뒤에야 실패로 끝났다. 배포 액션이 상태를 확인하는 간격에 상한이 없어 SDK 기본값인 600초까지 늘어난 탓이다. 이후 상한을 15초로 고쳤다.
- 감수한 것: main에 실패 커밋과 되돌림 커밋이, ECR에 실패 이미지와 수동 이미지가 남았다. 운영에서 일부러 실패를 일으켰는데, 실무라면 스테이징에서 하고 운영은 카나리나 블루/그린으로 영향 범위를 줄인다.
- 자세한 수치는 [measurements.md](../measurements.md)와 [잘못된 이미지 배포 기록](../troubleshooting/02-bad-image-rollback.md)에 있다.
