# DEC-25. 배포·롤백 시간을 운영 환경에서 실제 배포로 측정했다

- 상태: 확정 · 날짜: 2026-10-28 · 검증: 실측 완료
- 관련 이슈: https://github.com/DDongHyun00/3-tier-terraform-ecs/issues/36

## 배경

설계 품질 목표([architecture.md](../architecture.md) 12절)의 측정 항목은 "수동 대비 배포 소요 시간, 롤백 소요 시간"이다. E05 수동 배포 기록에는 롤링 2분 42초만 있고 빌드 시작 시각이 없어 전체 시간을 비교할 수 없었다. deploy.yml의 Step Summary(T0·T1·T2)는 머지부터 러너 시작까지의 대기를 재지 않고, T2에는 배포 액션의 안정화 폴링 지연이 섞인다. ECR 태그가 IMMUTABLE이라 측정할 때마다 `app/**`가 바뀐 새 main 브랜치 커밋이 필요했고, OIDC 신뢰 정책이 main 브랜치와 pull_request만 허용해서 실패 이미지도 main 브랜치를 거쳐야 했다. 당시(스테이징 구축 전)는 환경이 운영 하나뿐이었고 실사용자가 없는 데모였다.

## 결정 요인

- 항목이 "수동 대비"라 빌드부터 안정화까지 전 구간이 같은 날 같은 조건으로 있어야 표가 의미 있다.
- 롤백은 README와 `ecs.tf`에 적은 서킷 브레이커 자동 롤백이 실제로 도는지, 그동안 사이트가 살아 있는지까지 보여야 한다.
- main 스택을 띄우는 시간이 곧 비용이다. 측정은 한 세션에 끝내고 바로 destroy한다.

## 검토한 선택지

- D1 수동 기준값: (a) 측정 당일(10/28) 수동 배포를 1회 다시 잰다(가동 약 15분, 약 0.07 USD, ECR에 수동 이미지 1개 남음) / (b) E05 기록만 쓴다(빌드·push 칸이 "미측정").
- D2 자동 배포: (a) `app/**` 변경 PR을 머지해 push로 시작, 2회 / (b) workflow_dispatch(태그 불변이라 1회만 가능하고 캐시가 다 맞아 짧게 나옴).
- D3 실패 배포: (a) 운영 설정에서만 기동에 실패하는 코드를 머지해 파이프라인으로 배포 / (b) DB_URL을 틀린 태스크 정의를 CLI로 등록(워크플로의 실패 판정을 검증하지 못하고, 다음 배포가 틀린 설정을 물려받음).
- D4 롤백 측정 시점: (a) 지금 이슈 #36에서 재고 이슈 #42(E08)는 같은 데이터로 문서만 / (b) E08에서 다시 띄워 잰다.
- 폴링 지연: deploy.yml은 그대로 두고 ECS 이벤트 기준과 워크플로 종료 기준 두 값을 적는 쪽과, 폴링 최대 지연 옵션을 넣는 쪽을 비교했다. 후자는 이슈 범위 밖이라 뺐다.

## 결정

D1 (a), D2 (a) 2회(revert PR #68, Java 주석 PR #69), D3 (a)(PR #67, 앱이 `ASSETS_BUCKET`을 읽게 바꾸고 태스크 정의는 `S3_BUCKET` 그대로), D4 (a). deploy.yml은 고치지 않았다. 순서는 수동 배포 → 실패 배포·롤백 → 정상 배포 2회. #65 이후 새 apply가 ECR 최신 이미지로 뜨므로 정상 이미지가 마지막에 올라가야 했다. 시각은 PR mergedAt, run createdAt, 워크플로 단계 시각, ECR imagePushedAt, ECS 서비스 이벤트, CloudWatch 앱 로그에서 뽑았다.

## 결과

- 시작(머지) → 서비스 안정화(ECS 기준): 수동 5분 18초 / 자동 ① 5분 5초(캐시 적중) / 자동 ② 7분 38초(코드 변경). 워크플로 종료 기준은 ① 7분 18초, ② 10분 16초. ECS 롤링은 3분 16초 / 3분 21초 / 3분 22초로 거의 같았다.
- ②의 빌드·push 3분 58초 중 2분 36초는 GitHub Actions 캐시 내보내기(`cache-to: type=gha,mode=max`)였다. 벽시계 시간은 수동 최솟값과 비슷했고, 자동화로 줄어든 것은 사람이 하는 일(명령 13개 → 머지 1번)이었다.
- 롤백: 실패 배포 시작 → 실패 판정 4분 5초, 판정 → 이전 리비전 COMPLETED 1분 14초, 전체 5분 19초(머지부터 7분 44초). 새 태스크 5개가 모두 같은 예외로 죽었다. 그동안 liveness 5초 간격 217회가 전부 200이어서 무중단이었다.
- 워크플로는 롤백 완료 8분 33초 뒤에야 실패로 끝났다. 배포 액션의 안정화 대기에 최대 지연을 주지 않아 SDK 기본 최대 600초까지 폴링 간격이 늘어난 탓이다. 고치지 않고 PR #70 "남은 것"에 조치 후보로 적었다.
- 감수한 것: main 브랜치에 실패 커밋과 revert 커밋이, ECR에 실패 이미지와 수동 이미지가 남았다. 당시 환경이 운영 하나뿐이고 실사용자가 없는 데모라 운영에서 의도적으로 실패를 일으켰다. 실무라면 스테이징에서 하고, 운영에서는 카나리나 블루/그린으로 영향 범위를 줄인다.
