# DEC-31. 배포 이미지 빌드 캐시는 mode=max에서 mode=min으로 바꾼다

- 상태: 확정 · 날짜: 2026-10-29 · 검증: 실측 완료
- 관련 이슈: https://github.com/DDongHyun00/3-tier-terraform-ecs/issues/72

## 배경

이슈 #36에서 배포 시간을 재다가 deploy.yml의 빌드 단계가 `cache-to: type=gha,mode=max`로 중간 계층까지 전부 저장하는 것을 봤다. 코드를 바꾼 배포에서 빌드·push 3분 58초 중 캐시 내보내기가 2분 36초였다. 레포 캐시 한도는 10 GB다.

## 결정 요인

- `gh cache list`로 본 현재 캐시는 42개, 약 1.49 GiB라 용량은 문제가 아니었다. 문제는 시간이다.
- 실행마다 새로 저장되는 blob이 세 개(131.7 / 65.8 / 65.6 MiB, 합 약 263 MiB) 있었다. 빌더 단계의 bootJar·cp·jarmode extract 계층으로 보이고, 소스가 같았던 실행에서도 새로 생겼다. 저장만 하고 재사용은 안 되는 계층이다.
- [Docker 문서](https://docs.docker.com/build/cache/backends/#cache-mode)에서 min은 최종 이미지에 들어가는 계층만, max는 중간 계층까지 저장한다. 기본값은 min이다.

## 검토한 선택지

- A. max 유지: 다단계 빌드에서 적중률이 높다고 문서에 나오고 흔히 쓰는 설정이다. 그런데 매 커밋 바뀌는 계층에는 이득이 없고 내보내기 2분 36초를 감수해야 한다.
- B. min 전환: 바뀌는 중간층을 저장하지 않아 내보내기가 수 초로 줄어든다. 대신 빌더 단계의 Gradle 배포판·의존성 다운로드가 매번 생긴다(30초~1분 추정). 예상은 코드 변경 빌드 3분 58초 → 약 2분~2분 30초.
- C. min + Gradle 빌드를 Docker 밖(`gradle/actions/setup-gradle`)에서: 가장 바르지만 Dockerfile 구조가 바뀌고 이슈 범위 밖이다. 범위 밖으로 두었다.

## 결정

B. deploy.yml의 `cache-to`를 `type=gha,mode=min`으로 바꾼다. 측정은 두 번 한다. 재배포 1회(코드 변경 없음)와, 앱 주석 한 줄을 바꾸는 PR 1회(코드 변경 빌드)다. 결과가 예상과 다르면 A로 되돌리고 그 수치를 남긴다.

## 결과

| 측정 | 전(mode=max, #36) | 후(mode=min) |
| --- | --- | --- |
| 재배포(코드 변경 없음) 빌드·push | 1분 31초 | 4초(전부 CACHED, run 40826749426) |
| 코드 변경 빌드·push | 3분 58초 | 1분 19초(run 40829709064) |
| 캐시 내보내기 | 2분 36초 | 약 2초 |
| 실행당 새 캐시 | 약 263 MiB | 3개 132 KiB |

- 코드 변경 빌드 구간: dependencies 15초, bootJar 45초, extract 2초. 예상보다 빨랐고, 걱정한 재배포 지연은 없었다.
- 캐시 합계는 45개 1.49 GiB로 변화가 없었다. 되돌릴 이유가 없어 min을 유지한다.
- 범위 밖으로 남긴 것: 액션 버전을 커밋 SHA로 고정 + Dependabot, C안. 이 프로젝트에서는 범위 밖으로 두었다.
