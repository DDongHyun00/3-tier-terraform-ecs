# DEC-31. 배포 이미지 빌드 캐시를 mode=max에서 mode=min으로 바꿨다

- 상태: 확정
- 날짜: 2026-10-29

## 배경

배포 시간을 재다가 배포 워크플로의 빌드 단계가 `cache-to: type=gha,mode=max`로 중간 계층까지 전부 저장하는 것을 봤다. 코드를 바꾼 배포에서 빌드와 push 3분 58초 가운데 2분 36초가 캐시 내보내기였다.

고려한 것:
- 레포 캐시 한도는 10 GB인데, `gh cache list`로 본 캐시는 42개 약 1.49 GiB였다. 용량보다 시간이 문제였다.
- 실행마다 새로 저장되는 blob이 세 개(131.7, 65.8, 65.6 MiB, 합 약 263 MiB) 있었다. 빌더 단계의 bootJar, cp, jarmode extract 계층으로 보였고, 소스가 같은 실행에서도 새로 생겼다. 저장만 하고 다시 쓰이지 않는 계층이었다.
- [Docker 문서](https://docs.docker.com/build/cache/backends/#cache-mode)에 따르면 min은 최종 이미지에 들어가는 계층만, max는 중간 계층까지 저장한다. 기본값은 min이다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| max 유지 | 다단계 빌드에서 캐시 적중률이 높아 흔히 쓴다 | 매번 바뀌는 계층에는 이득이 없고 내보내기 2분 36초를 계속 치른다 |
| min으로 전환 | 바뀌는 중간 계층을 저장하지 않아 내보내기가 수 초로 준다 | 빌더 단계의 Gradle과 의존성 다운로드가 매번 생길 수 있다(30초~1분 추정) |
| min과 함께 Gradle 빌드를 Docker 밖에서 | 가장 바른 구조다 | Dockerfile 구조가 바뀌어 이번 범위를 넘는다 |

## 결정

min으로 바꿨다. 예상은 코드 변경 빌드가 3분 58초에서 약 2분~2분 30초로 주는 것이었다. 재배포 1회(코드 변경 없음)와 앱 주석 한 줄을 바꾼 PR 1회로 재서, 예상과 다르면 max로 되돌리기로 했다.

## 결과

| 측정 | mode=max | mode=min |
|---|---|---|
| 재배포(코드 변경 없음) 빌드와 push | 1분 31초 | 4초 (전부 캐시 적중) |
| 코드 변경 빌드와 push | 3분 58초 | 1분 19초 |
| 캐시 내보내기 | 2분 36초 | 약 2초 |
| 실행마다 새로 생긴 캐시 | 약 263 MiB | 3개 132 KiB |

- 코드 변경 빌드는 의존성 15초, bootJar 45초, extract 2초였다. 예상보다 빨랐고, 걱정한 재배포 지연도 없었다.
- 캐시 합계는 45개 1.49 GiB로 그대로였다. 되돌릴 이유가 없어 min을 유지했다.
- 액션 버전을 커밋 SHA로 고정하고 Dependabot을 붙이는 것, Gradle 빌드를 Docker 밖으로 빼는 것은 이 프로젝트 범위 밖으로 뒀다.
