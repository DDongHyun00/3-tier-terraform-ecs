# DEC-36. 컴퓨트를 Fargate에서 ECS on EC2로 전환한다

- 상태: 확정 · 날짜: 2026-10-30 · 검증: 예상
- 관련 이슈: https://github.com/DDongHyun00/3-tier-terraform-ecs/milestone/10

## 배경

기획서 단계(E02)에서 컴퓨트는 ECS Fargate로 정했다. 그때 비교 대상은 EKS(제어 플레인 월 73달러)였고 ECS on EC2는 따로 저울에 올리지 않았다(`docs/architecture.md` 298행). 일주일 범위에서 서버 관리를 빼는 게 목적이었다. E07까지 끝내고 현직 클라우드 엔지니어에게 조언을 들었다. 호스트에 node_exporter·cAdvisor를 깔아 Prometheus·Grafana로 거의 실시간으로 보고, 비용 때문에 CloudWatch는 잘 안 쓴다는 내용이었다. Fargate는 호스트가 없어 그 구조를 그대로 못 쓴다.

## 결정 요인

- 비용은 이 규모에서 거의 같다(Fargate 태스크 2개 시간당 약 0.057 USD vs t4g.small 2대 약 0.042 USD, 24시간 기준 월 10달러 안팎). 전환 근거는 비용이 아니라 호스트 수준 관측과 운영 범위(용량 공급자·ASG·AMI·호스트 수집기)를 보여 주는 것이다.
- E07에서 ECS 서비스 지표가 약 4분 늦게 도착해 CPU 알람이 안 울리는 것을 실측했다. 호스트 수집기는 15초 단위다.
- E08·E09에 영향이 크다. 장애 재현은 준비된 대로 먼저 하고, 비용 분석과 README는 최종 구조 뒤에 한다.

## 검토한 선택지

|  | Fargate 유지 | ECS on EC2 전환 |
| --- | --- | --- |
| 표준 | AWS 기본 권장, 서버 관리 없음 | 비용·제어·호스트 수집기가 필요할 때의 선택. 둘 다 표준 |
| 실무 | 소규모 팀, 운영 인력 적을 때 | 규모가 크거나 운영팀이 있는 회사. 비용을 따지는 회사가 많이 쓴다(현직 조언) |
| 포트폴리오 | 단순함을 설명 | 호스트 운영·2단계 스케일링·수집기 설치를 보여 줌. "왜 전환했나"에 비용이 아니라 관측·운영 범위로 답해야 설득력 |
| 기능 차이 | 없음(앱 동작 같음) | 인스턴스 패치·드레인·용량 공급자 관리가 생김. 오토스케일링 2단계 |
| 작업량 | 0 | 3~4일 + apply 세션 1~2회, 완성 약 1주 지연 |

## 결정

ECS on EC2로 전환한다. 순서는 E08(준비 완료) → E10 전환 → E11 통합 모니터링 → E12 중앙 로그 → E09 비용·마무리. 비용 주장은 추정이 아니라 E09 청구액으로 검증한다. Fargate 선택의 근거(일주일 범위·서버 관리 제거, EKS만 비교)는 이 기록에 소급해 남긴다.

## 결과

- 얻을 것: 호스트 수집기 기반 관측(E11), 운영 범위 확대, Fargate/EC2 실측 비교.
- 감수한 것: 완성 약 1주 지연, compute 모듈·배포 역할 권한 재작업, 측정 일부 재실행.
