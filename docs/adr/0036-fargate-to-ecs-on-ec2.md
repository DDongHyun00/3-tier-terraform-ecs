# DEC-36. 컴퓨트를 Fargate에서 ECS on EC2로 바꿨다

- 상태: 확정
- 날짜: 2026-10-30

## 배경

설계할 때 컴퓨트는 ECS Fargate로 정했다. 프로젝트 범위에서 서버 관리를 빼는 게 목적이었고, 비교 대상은 EKS(제어 플레인만 월 73 USD)였다. ECS on EC2는 그때 따로 따져 보지 않았다.

오토스케일링 시험까지 끝내고 관측 방식을 다시 봤다. CloudWatch의 ECS 서비스 지표가 약 4분 늦게 들어와 CPU 알람이 울리지 않는 것을 실측했다. 호스트에 node_exporter와 cAdvisor를 깔아 Prometheus로 15초마다 보려면 호스트가 있어야 하는데, Fargate에는 호스트가 없다.

고려한 것:
- 이 규모에서 비용은 거의 같다. Fargate 태스크 2개가 시간당 약 0.057 USD, t3.small 2대가 볼륨을 포함해 약 0.059 USD다([cost.md](../cost.md)).
- 그래서 바꿀 이유는 비용에 있지 않았다. 호스트 수준 관측, 그리고 용량 공급자와 ASG, AMI, 호스트 수집기까지 운영 범위를 넓혀 보는 데 있었다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| Fargate 유지 | 서버 관리가 없고 소규모 팀에 맞는 기본 선택이다 | 호스트가 없어 호스트 수집기를 쓸 수 없다 |
| ECS on EC2로 전환 | 호스트 관측과 태스크, 인스턴스 두 단계 스케일링을 직접 다룬다 | 인스턴스 패치와 드레이닝, 용량 공급자 관리가 생기고 compute 모듈과 배포 역할을 다시 만들어야 한다 |

## 결정

ECS on EC2로 바꿨다. 비용이 비슷하다는 주장은 요금표 추정에서 끝내지 않고 실제 청구액으로 확인하기로 했다.

## 결과

- 얻은 것: 호스트 수집기 기반 관측(Prometheus, Grafana), 태스크와 인스턴스 두 단계 스케일링 실측, Fargate와 EC2를 같은 방법으로 잰 비교 자료
- 감수한 것: compute 모듈과 배포 역할 권한을 다시 만들었고, 측정 일부를 다시 했다.
- 바꾼 뒤 비용 차이는 8시간 세션 기준 약 0.04 USD(2%)였다. 응답은 안정 구간 ALB p95가 30 ms에서 114 ms로 느려졌고 원인은 찾지 못했다.
- destroy 때 NAT가 먼저 지워져 서비스가 멈추는 사고처럼, Fargate에 없던 운영 문제도 실제로 겪었다.
