# DEC-40. VPC를 관제, 운영, 스테이징 3개로 나누고 피어링으로 이었다

- 상태: 확정 (관제와 스테이징 사이 피어링은 만들지 않았다)
- 날짜: 2026-11-01

## 배경

처음에는 관제 VPC 하나를 앱 VPC와 피어링하는 2개 구성으로 정했다. 그런데 VPC가 2개면 관제 서버가 보는 대상이 앱 VPC 하나뿐이라, 왜 같은 VPC에 두지 않고 나눴는지 설명하기 어려웠다. 그래서 VPC 개수와 연결 방식을 다시 조사했다.

고려한 것:
- AWS 다중 VPC 백서는 연결할 VPC가 10개 미만이면 피어링이 비용이 가장 낮고 성능이 가장 좋다고 한다([VPC peering](https://docs.aws.amazon.com/whitepapers/latest/building-scalable-secure-multi-vpc-network-infrastructure/vpc-peering.html)).
- 피어링은 전이 라우팅을 하지 않는다. 관제와 운영, 관제와 스테이징만 이으면 운영과 스테이징은 따로 막지 않아도 통하지 않는다([VPC peering 제한](https://docs.aws.amazon.com/vpc/latest/peering/vpc-peering-basics.html)).
- 서울 Transit Gateway는 연결 하나에 시간당 0.07 USD, 데이터 GB당 0.02 USD가 붙는다. 피어링은 시간 요금이 없다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| VPC 2개와 피어링 | 비용이 그대로다 | 관제를 따로 뗀 이유가 약하다 |
| VPC 3개와 피어링 | 환경 분리와 공용 서비스 분리를 둘 다 보여 준다 | VPC가 늘어 세션 비용이 는다 |
| VPC 3개와 Transit Gateway | 허브 구조라 VPC가 늘어도 정리하기 쉽다 | 3개 규모에는 과하고 연결 요금이 붙는다 |

## 결정

VPC 3개와 피어링을 골랐다. 관제 10.100.0.0/16, 운영 10.0.0.0/16, 스테이징 10.1.0.0/16으로 나누고, 피어링은 관제와 운영, 관제와 스테이징 2개로 설계했다. 보안 그룹은 관제에서 앱 인스턴스의 지표 포트로, 앱에서 관제의 로그 포트로 가는 길만 연다. 관제 VPC에는 인터넷 입구를 두지 않고 SSM으로만 접속한다.

## 결과

VPC 3개와 CIDR 분리는 설계대로 됐다. 관제 서버가 죽어도 운영 서비스는 영향을 받지 않고, 운영과 스테이징은 라우팅만으로 격리된다.

피어링은 관제와 운영 사이 1개만 만들었다. 스테이징 루트(`terraform/staging`)에는 피어링을 넣지 않아서 스테이징은 관제 서버가 보지 않는다. 스테이징은 배포 워크플로의 스모크 테스트로 확인하고, 스테이징까지 한 곳에서 보는 모니터링은 하지 못했다.

VPC가 늘어난 만큼 세션 비용도 늘었다. VPC가 10개를 넘거나 NAT를 한곳에 모아야 하면 그때는 Transit Gateway로 옮겨야 한다.
