# DEC-46. 태스크 사양을 0.25 vCPU / 0.5 GB에서 0.5 vCPU / 1 GB로 올렸다

- 상태: 확정
- 날짜: 2026-10-21

## 배경

태스크를 0.25 vCPU / 0.5 GB로 처음 띄웠더니 앱 기동에 120초가 걸렸다("Started BoardApplication in 120.585 seconds", 로컬은 11초). 헬스체크 유예 60초보다 길어서 태스크가 계속 교체됐고, 유예를 임시로 240초까지 늘렸다. 사이트도 느렸다. ALB 평균 응답은 0.1~0.2초였지만 최대 2.8~3.9초가 나왔고, 이미지를 첨부한 글쓰기는 4~5초 걸렸다. 코드에 N+1 쿼리는 없었다(JOIN FETCH, BatchSize, 배치 카운트).

고려한 것:
- 기동 120초는 재배포, 스케일 아웃, 장애 복구 시간을 모두 늘린다. 뒤에 할 오토스케일링 시험과 장애 실험의 수치가 이 값에 묶인다.
- Fargate 요금(서울 vCPU 0.04656, GB 0.00511 USD/시간) 기준으로 태스크 2개가 시간당 0.028에서 0.057 USD로 두 배가 된다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 0.25 vCPU 유지, 유예 240초 | 비용이 그대로다 | 기동 2분과 느린 첫 요청을 계속 안고 간다 |
| 0.5 vCPU / 1 GB와 JVM 옵션 | 이미지를 다시 빌드하지 않고 태스크 정의만 바꾸면 된다 | 비용이 두 배다 |

## 결정

0.5 vCPU / 1 GB로 올렸다. `task_cpu`를 256에서 512로, `task_memory`를 512에서 1024로 바꾸고, 태스크 환경 변수에 `JAVA_TOOL_OPTIONS = "-XX:MaxRAMPercentage=75.0 -XX:TieredStopAtLevel=1"`을 넣었다. 바꾸기 전과 뒤를 같은 명령(`curl -w '%{time_total}'`, 기동 로그)으로 재서 비교했다.

## 결과

2026-10-22 측정:

| 항목 | 0.25 vCPU | 0.5 vCPU |
|---|---|---|
| 앱 기동 | 121.5초 / 123.0초 | 23.1초 / 23.1초 |
| `/posts` 첫 요청과 재요청 | 0.47초, 0.06초 | 0.13초, 0.08초 |
| `/login` | 0.05초 | 0.06~0.10초 |

- 기동이 약 122초에서 23초로 다섯 배 빨라졌다. 이 덕분에 오토스케일링 시험에서 새 태스크가 늘림 결정 뒤 80초 안에 정상이 됐다.
- 워밍업 뒤 단순 페이지 응답은 둘 다 0.1초 안팎으로 차이가 없었다. 느렸던 원인은 평소 CPU 부족보다 기동 직후의 JIT 컴파일과 초기화였다.
- 감수한 것: Fargate 비용이 두 배가 됐다(시간당 +0.029 USD, 24시간 가동이면 월 +21.17 USD).
- 못 잰 것: 0.5 vCPU에서 첫 글쓰기가 얼마나 빨라졌는지는 재지 못했다. 글쓰기 측정은 바꾸기 전과 뒤 모두 0.25 vCPU 태스크에서 나왔다.
