# 잘못된 이미지 배포와 자동 롤백

운영에서만 기동에 실패하는 이미지를 일부러 배포하고, ECS 배포 서킷 브레이커가 얼마나 빨리 되돌리는지와 그동안 사용자 응답을 쟀다.

## 요약

2026-10-28에 Fargate 태스크 2개로 쟀다. 롤링 배포는 최소 100%, 최대 200%였고 서킷 브레이커 롤백을 켜 둔 상태였다.

스테이징을 만들기 전이라 이 실험도 운영 환경에서 했다. 실사용자가 없는 데모여서 가능했다.

| 항목 | 값 |
|---|---|
| 실패 판정까지 | 4분 5초 |
| 판정부터 이전 버전 복귀까지 | 1분 14초 (합계 5분 19초) |
| 머지부터 이전 버전 복귀까지 | 7분 44초 |
| 사용자 응답 | liveness 217회(5초 간격) 모두 200 |
| 울린 알람 | 없음 |

서비스 요청 전체는 재지 않았다. 사용자 응답은 liveness 기록으로만 확인했다.

## 재현

CI는 통과하고 운영 설정에서만 기동에 실패하는 변경을 골랐다. CI가 잡지 못하는 설정 오류를 재현하고 싶었다.

- 앱이 버킷 이름을 읽는 환경 변수를 `S3_BUCKET`에서 `ASSETS_BUCKET`으로 바꿨다.
- 태스크 정의는 그대로 `S3_BUCKET`을 넣는다. 운영(`STORAGE_TYPE=s3`)에서는 버킷 값이 비어 `S3FileStorage` 생성자가 예외를 던지고 컨테이너가 종료된다.
- 테스트는 로컬 저장소를 쓰기 때문에 CI는 통과했다.

이 변경을 main에 머지하자 배포 워크플로가 이미지(태그 `d96d10d`)를 빌드해 ECR에 올리고 태스크 정의 리비전 `:8`로 서비스를 갱신했다. 그동안 `/actuator/health/liveness`를 5초 간격으로 요청해 기록했다.

## 무슨 일이 있었나

| 시각 (KST) | 일 |
|---|---|
| 15:20:43 | main에 머지 |
| 15:23:07 | 새 배포(리비전 `:8`) 시작 |
| 15:23:21 ~ 15:26:42 | 새 태스크 5개가 차례로 시작해 모두 같은 예외로 종료 |
| 15:27:13 | 서킷 브레이커가 실패로 판정, 롤백 시작 |
| 15:28:27 | 이전 버전(`:7`)으로 안정 |
| 15:37:06 | 배포 워크플로가 실패로 끝남 |

그동안 기존 태스크 2개가 요청을 계속 받았다. liveness 217회가 모두 200이었고 가장 느린 응답은 0.36초였다. 새 태스크는 기동 중에 바로 종료돼 타깃 그룹에서 정상이 된 적이 없다. 그래서 ALB가 실패한 태스크로 요청을 보낸 적도 없다.

배포 워크플로는 롤백이 끝나고 8분 33초가 지나서야 실패를 알렸다. 배포 액션이 서비스 상태를 확인하는 간격이 최소 15초에서 시작해 지수로 늘어나고, 상한이 SDK 기본값 600초였기 때문이다. 오래 기다린 배포일수록 결과를 늦게 안다.

## 원인

설계대로 동작했다. 롤백이 일어난 이유와 사용자 응답이 실패하지 않은 이유는 당시 서비스 설정 두 가지다(`terraform/modules/compute/ecs.tf`).

    deployment_minimum_healthy_percent = 100
    deployment_maximum_percent         = 200

    deployment_circuit_breaker {
      enable   = true
      rollback = true
    }

- 서킷 브레이커의 임계값은 실패한 태스크 수다. 원하는 태스크 수의 50%이고 최소 3이라 태스크 2개에서는 3이었다. 실패가 3건이 되자 배포를 실패로 판정하고 직전 배포로 되돌렸다.
- 실제로 실패한 태스크는 5개였다. 실패가 3건이 된 순간 이미 시작된 태스크가 더 있었기 때문이다. 판정까지 4분 5초가 걸린 것도 태스크가 하나씩 기동을 시도하고 종료되기를 반복해서다.
- 최소 정상 비율이 100%라 기존 태스크를 먼저 내리지 않았다. 롤링 배포는 기존 2개를 그대로 둔 채 새 태스크를 더 띄우고, 새 태스크가 정상이 된 뒤에야 기존 것을 뺀다. 새 태스크가 한 번도 정상이 되지 않았으니 기존 2개가 끝까지 남았다.

## 조치와 재발 방지

롤백은 서킷 브레이커가 자동으로 했다. 직접 한 조치는 코드를 되돌린 것 하나다. 자동 롤백은 서비스만 되돌리고 main의 코드와 ECR의 최신 이미지는 그대로 둔다. 다음 apply는 ECR 최신 이미지로 뜨기 때문에, 버킷 변수를 `S3_BUCKET`으로 되돌리는 PR을 머지해 정상 이미지를 다시 최신으로 만들었다.

지금 설정의 보호 장치:
- 기동에 실패하는 이미지가 배포돼도 서비스가 내려가지 않는다.
- 실패한 배포는 사람 없이 직전 버전으로 돌아간다.

지금은 최소 정상 비율이 50%다([Spot 회수](07-spot-interruption.md)에 맞춘 설정). 실패한 배포 중에 옛 태스크 1개가 먼저 내려갈 수 있다. 용량은 절반이 되지만 서비스가 끊기지는 않는다.

워크플로가 실패를 늦게 알리던 문제는 확인 간격의 상한을 15초로 두어 고쳤다. 정상 배포 두 번에서 서비스 안정과 워크플로 종료의 차이가 1초 미만과 3초인 것을 확인했다. 롤백 때 알림 시간은 고친 뒤 다시 재지 않았다.

## 배운 점과 개선 방향

배운 점:
- 서킷 브레이커만으로도 기동에 실패하는 이미지는 사람 없이 되돌아갔고, 그동안 기존 태스크가 응답을 이어 갔다.
- 배포 실패는 사용자 오류를 만들지 않아서 5xx 비율 알람이나 비정상 타깃 알람으로는 잡히지 않는다.
- 자동 롤백은 서비스만 되돌린다. main의 코드와 ECR의 최신 이미지는 사람이 되돌려야 했다.

개선 방향:
- EventBridge 규칙으로 `ECS Deployment State Change` 이벤트 중 `SERVICE_DEPLOYMENT_FAILED`를 잡아 기존 SNS 토픽으로 보내면 된다. 콘솔이나 CLI로 한 배포까지 경로와 상관없이 실패를 바로 알 수 있다.
- ECS 배포 알람을 서킷 브레이커와 함께 두는 게 맞다. 지정한 CloudWatch 알람이 울리면 배포를 실패로 보고 되돌리기 때문에, 기동은 되지만 5xx가 늘어나는 이미지도 잡는다. 둘을 같이 쓰면 먼저 조건이 찬 쪽이 롤백을 일으킨다([ECS 배포 알람](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-alarm-failure.html)).
- 트래픽을 한꺼번에 넘기지 않으려면 ECS 카나리 배포로 일부 트래픽만 먼저 보내 지켜본 뒤 나머지를 넘기면 된다([ECS 카나리 배포](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/canary-deployment.html)).
