# 잘못된 이미지 배포 후 자동 롤백

운영에서만 기동에 실패하는 이미지를 main에 머지해 배포했다. ECS 배포 서킷 브레이커가 실패를 판정하고 직전 리비전으로 되돌렸다. 그동안 측정한 liveness 요청 217회에서 실패는 0건이었다. 게시판 요청 전체는 측정하지 않았다.

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-28 (시각은 KST) |
| 환경 | prod (환경이 하나라 운영에서 의도적으로 실험했다. 실무라면 스테이징에서 한다) |
| 구성 | ECS Fargate 태스크 2개, 롤링 배포 최소 100% / 최대 200%, 서킷 브레이커 rollback 켬 |
| 사용자 영향 | 측정한 liveness 요청(5초 간격) 217회 중 실패 0건. 게시판 요청 전체는 측정하지 않았다 |
| 롤백 시간 | 실패 배포 시작 → 실패 판정 4분 5초, 판정 → 이전 리비전 복귀 1분 14초, 전체 5분 19초 (머지부터 7분 44초) |
| 울린 알람 | 없음 (CloudWatch 알람은 다음 날 E07에서 만들었다. 지금 알람으로도 잡히지 않는 이유는 재발 방지 절) |
| 사람이 한 조치 | 없음 (롤백은 자동). 코드는 revert PR로 되돌렸다 |

이 실험은 E06 배포·롤백 시간 측정(#36)과 같은 세션에서 했고, 수치는 README `## 측정`의 롤백 소요 시간과 같다.

## 재현 방법

CI는 통과하고 운영 설정에서만 기동에 실패하는 변경을 골랐다. "CI가 못 잡은 설정 오류"를 재현하기 위해서다.

- 변경([PR #67](https://github.com/DDongHyun00/3-tier-terraform-ecs/pull/67)): 앱의 `app.storage.s3.bucket`이 읽는 환경 변수 이름을 `S3_BUCKET`에서 `ASSETS_BUCKET`으로 바꿨다.
- 태스크 정의는 그대로 `S3_BUCKET`을 넣는다. 운영(`STORAGE_TYPE=s3`)에서는 버킷 값이 비어 `S3FileStorage` 생성자가 예외를 던지고 컨테이너가 종료된다.
- 테스트는 local 저장소를 쓰므로 CI app-test는 통과했다.
- PR #67을 main에 머지하자 deploy 워크플로가 자동으로 돌았다([run 40643279590](https://github.com/DDongHyun00/3-tier-terraform-ecs/actions/runs/40643279590)). 이미지를 빌드해 ECR에 올리고(태그 d96d10d) 태스크 정의 리비전 :8로 서비스를 갱신했다.
- 확인 중에는 사이트 liveness(`/actuator/health/liveness`)를 5초 간격으로 요청해 상태 코드와 응답 시간을 남겼다(15:18:27~15:38:02).

## 원인

설계대로 동작했다. 롤백이 일어난 이유와 liveness 요청이 실패하지 않은 이유는 서비스 설정 두 가지다(`terraform/modules/compute/ecs.tf`).

    deployment_minimum_healthy_percent = 100
    deployment_maximum_percent         = 200

    deployment_circuit_breaker {
      enable   = true
      rollback = true
    }

- **서킷 브레이커 임계값은 실패한 태스크 수로 정해진다.** 임계값은 원하는 태스크 수 × 50%이고 최소 3이다. 태스크가 2개라 임계값은 3이었다. 새 태스크가 기동 중 종료될 때마다 실패 수가 늘고, 3에 닿자 배포를 실패로 판정하고 `rollback = true`에 따라 직전 배포로 되돌렸다.
- 실제로 실패한 태스크는 5개였다. 실패 수가 3이 됐을 때 이미 시작된 태스크가 더 있었기 때문이다. 실패 판정까지 4분 5초가 걸린 것도 태스크가 하나씩 기동을 시도하고 종료되기를 반복했기 때문이다.
- **최소 정상 비율 100%라 기존 태스크를 먼저 내리지 않는다.** 롤링 배포는 기존 2개를 유지한 채 새 태스크를 최대 200%까지 더 띄우고, 새 태스크가 healthy가 된 뒤에야 기존 것을 뺀다. 새 태스크가 한 번도 healthy가 되지 않았으므로 기존 2개는 그대로 남았다.

## 해결

- 롤백은 서킷 브레이커가 자동으로 했다. 내가 한 조치는 없다. 판정 1분 14초 뒤 이전 리비전(:7)으로 서비스가 안정화됐다.
- 자동 롤백은 서비스만 되돌리고 main의 코드와 ECR 최신 이미지는 그대로 둔다. 그래서 revert [PR #68](https://github.com/DDongHyun00/3-tier-terraform-ecs/pull/68)로 버킷 환경 변수를 다시 `S3_BUCKET`으로 되돌렸다. 이 머지로 정상 배포가 한 번 더 돌았고 ECR 최신 이미지도 정상 이미지로 돌아왔다(다음 apply가 ECR 최신 이미지로 뜨기 때문에 필요했다).

## 재발 방지

지금 설정이 막는 것:
- 기동에 실패하는 이미지가 배포돼도 서비스가 내려가지 않는다(롤링 100% / 200%).
- 실패한 배포는 사람 없이 직전 리비전으로 돌아간다(서킷 브레이커 rollback).

남은 위험:
- **배포 실패를 알리는 알람이 없다.** 실험 다음 날(E07) 만든 알람 5개(5xx 비율, 비정상 타깃, ECS CPU, RDS 연결 수, RDS 스토리지)도 이런 실패는 잡지 못한다. 실패한 태스크는 healthy가 된 적이 없고 기존 태스크가 계속 응답했기 때문에 비정상 타깃도 5xx도 생기지 않았다.
- 실패를 알려 준 것은 GitHub Actions 워크플로 실패뿐이었고, 그것도 롤백 완료 8분 33초 뒤였다. #71에서 배포 액션의 폴링 간격 상한을 15초(`wait-max-delay-seconds: 15`)로 두었고, 정상 배포 2회에서 안정화와 워크플로 단계 종료의 차이가 1초 미만·3초인 것을 확인했다. 롤백 때의 실패 알림 지연은 다시 재지 않았다.
- 워크플로를 거치지 않은 배포(콘솔·CLI에서 한 서비스 갱신)는 실패해도 알림이 없다.

제안(구현 안 함): EventBridge 규칙으로 `ECS Deployment State Change` 이벤트 중 `SERVICE_DEPLOYMENT_FAILED`를 잡아 기존 SNS 토픽(Slack 경로)으로 보낸다. 실무에서 흔히 쓰는 방식이고, 배포 경로와 상관없이 실패를 바로 알 수 있다. 별도 이슈로 판단한다.

## 예상과 달랐던 것

- 서킷 브레이커가 실패를 판정하고 롤백까지 끝냈는데, 워크플로는 그 뒤로 8분 33초 동안 계속 기다리다 실패로 끝났다. 원인은 배포 액션(`amazon-ecs-deploy-task-definition@v2`)이 서비스 안정화를 폴링할 때 최소 간격 15초만 주고 최대 간격은 SDK 기본값 600초를 쓰는 것이었다. 폴링 간격이 지수로 늘어 오래 기다린 배포일수록 결과를 늦게 안다. 롤백은 대기 시작 5분 19초 뒤에 끝나 다음 폴링까지 8분 넘게 걸렸다. #71에서 폴링 간격 상한을 15초로 두었다. E07 세션의 정상 배포 2회에서 안정화와 워크플로 단계 종료의 차이가 1초 미만·3초인 것을 확인했지만, 롤백 때의 실패 알림 지연은 다시 재지 않았다.
