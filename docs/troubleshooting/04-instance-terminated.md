# 컨테이너 인스턴스 종료

컴퓨트를 Fargate에서 ECS on EC2로 바꾸면서 생긴 새 장애 지점을 재현했다. 태스크가 올라가 있는 EC2 인스턴스 1대를 꺼서, 그 위의 태스크가 어디로 옮겨 가고 사용자가 얼마나 영향을 받는지 쟀다. Fargate에서는 호스트가 보이지 않아 없던 시나리오다.

## 요약

2026-11-02 13:44 KST에 쟀다. t3.small 2대(2a, 2c)에 인스턴스마다 태스크 1개씩 올라가 있었고, 용량 공급자의 관리형 종료 보호와 관리형 드레이닝이 켜져 있었다.

이것도 스테이징이 없던 때라 운영 인스턴스를 직접 껐다.

| 항목 | 값 |
|---|---|
| 사용자 영향 | ALB 지표로는 0초. 클라이언트 쪽은 확정하지 못함 |
| 새 태스크가 정상이 되기까지 | 88초 |
| 대체 인스턴스가 클러스터에 등록되기까지 | 47초 이내 |
| 옛 인스턴스가 꺼지기까지 | 4분 30초 |
| 울린 알람 | 없음 |

사용자 영향은 ALB 지표로만 판단했다. 응답 기록을 종료 명령 46초 뒤에야 켜서 처음 46초는 클라이언트 쪽 기록이 없다.

## 재현

- 서비스 태스크 2개(2a, 2c), 인스턴스 2대, 배포나 스케일링이 진행 중이 아닐 때
- 용량 공급자 `3tier-prod-ec2`: 관리형 종료 보호, 관리형 드레이닝 켬
- 타깃 그룹 헬스체크 `/actuator/health/liveness`, 15초 간격, 정상 2회와 비정상 2회, 등록 해제 지연 30초

1. 사용자 쪽 응답을 1초마다 기록한다.

        powershell -NoProfile -ExecutionPolicy Bypass -File scripts/probe.ps1 -Url https://3tier.link/posts,https://3tier.link/actuator/health,https://3tier.link/actuator/health/liveness -IntervalSeconds 1 -MaxTimeSeconds 600 -OutFile <경로>

2. ASG 명령으로 인스턴스 1대(여기서는 2a)를 끈다. 원하는 용량을 줄이지 않으므로 ASG가 대체 인스턴스를 띄운다.

        aws autoscaling terminate-instance-in-auto-scaling-group --instance-id <인스턴스 ID> --no-should-decrement-desired-capacity --profile 3tier

### 예상

전원이 바로 꺼지는 하드웨어 장애처럼 동작할 거라고 봤다. 그 위의 태스크가 바로 죽고, ALB 헬스체크가 죽은 타깃을 떼기까지 30~40초 동안 요청 절반이 502나 504로 실패한다. 남은 인스턴스에는 빈자리가 없어 새 태스크는 대체 인스턴스가 뜰 때까지 기다리고, 복귀까지 3분 안팎이 걸린다. 비정상 타깃 알람이 울릴 수도 있다.

## 무슨 일이 있었나

| 시각 (KST) | 일 |
|---|---|
| 13:44:10 | ASG가 종료 요청을 받고 수명 주기 훅에서 대기 |
| 13:44:16 | 대체 인스턴스 기동 시작 |
| 13:44:34 | 새 태스크 생성, 자리를 기다림 |
| 13:44:57 | 옛 인스턴스 DRAINING. 그 위 태스크는 계속 정상. 대체 인스턴스는 이미 등록됨 |
| 13:45:38 | 새 타깃 등록, 정상 타깃 3개 |
| 13:46:36 | 옛 태스크 정지 |
| 13:46:46 | 옛 타깃 제외 |
| 13:48:40 | 옛 인스턴스 종료 |

예상과 달리 인스턴스는 바로 꺼지지 않았고 순서대로 교체됐다. 새 태스크가 정상이 된 뒤에야 옛 태스크가 내려갔고, 정상 타깃 수는 2개에서 3개, 다시 2개로 움직였다. 비정상 타깃은 한 번도 없었다. 13:44~13:48 동안 ALB의 5xx와 타깃 연결 오류는 0이었고 분당 요청 수도 일정했다. 대체 인스턴스는 예상(90초)보다 빠른 47초 안에 등록됐다.

응답 기록은 649건이었고 HTTP 오류는 0건이었다. 다만 13:47에 시작한 요청 21건이 21초 만에 시간 초과로 끝났다. 서버 쪽 지표에는 오류가 없었고 같은 초의 다른 요청은 정상이었다. 클라이언트 쪽 네트워크를 의심하지만 분 단위 합계로는 21건이 서버에 닿았는지 가릴 수 없어서 원인은 확인하지 못했다. 그래서 사용자 영향은 "ALB 지표 기준 0초"로 한정해 적었다.

## 원인

두 설정이 맞물려 사용자 영향이 0이었다.
- 관리형 드레이닝: 용량 공급자가 ASG에 종료 수명 주기 훅을 걸어 둔다. 종료 요청이 오면 ECS가 인스턴스를 DRAINING으로 바꾸고, 그 위의 태스크는 대체 태스크가 다른 곳에서 정상이 될 때까지 요청을 계속 받는다([관리형 인스턴스 드레이닝](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/managed-instance-draining.html)).
- 원하는 용량 유지: ASG가 곧바로 대체 인스턴스를 띄워, 빈자리가 없던 클러스터에 47초 만에 새 태스크 자리가 생겼다.

이 흐름은 ASG가 종료를 주관할 때만 해당한다. 스케일 인, 인스턴스 새로 고침, ASG를 통한 수동 종료가 여기에 들어간다. 하드웨어 장애나 `ec2 terminate-instances`처럼 훅을 거치지 않는 정지는 재지 않았다. 그 경우에는 예상한 30~40초 실패가 그대로 나올 것으로 본다.

## 조치와 재발 방지

사람이 한 조치는 없다. ECS가 드레이닝과 태스크 교체를, ASG가 대체 인스턴스를 맡았고 교체 전체에 4분 30초가 걸렸다.

지금 설정의 보호 장치:
- 관리형 종료 보호와 드레이닝 덕분에 ASG가 주관하는 종료에서는 태스크가 있는 인스턴스가 보호되거나 비워진 뒤 꺼진다. 같은 날 스케일 인(4대에서 2대)에서도 태스크가 있는 2대는 남고 빈 2대만 꺼졌다.
- 태스크를 가용 영역마다 1개씩 두고, ASG 상한을 태스크 상한의 2배(8대)로 둬서 교체나 배포 때 새 태스크를 놓을 인스턴스가 늘 생긴다.

## 배운 점과 개선 방향

배운 점:
- 관리형 종료 보호와 드레이닝이 있으면 ASG가 주관하는 종료에서는 태스크를 비운 뒤에 인스턴스가 꺼진다.
- 응답 기록을 종료 명령보다 늦게 켜서 사용자 영향을 ALB 지표로만 판단해야 했다. 측정 도구는 사건보다 먼저 켜야 한다.
- 대체 인스턴스가 뜰 때까지 용량이 절반이다. 부하 중이었다면 짧게는 CPU 알람, 길게는 스케일 아웃이 겹쳤을 것이다. 대기 인스턴스는 비용이 들어 이때는 두지 않았고, 나중에 Spot 쪽에만 1대를 뒀다([Spot 회수](07-spot-interruption.md)).
- 하드웨어 장애처럼 인스턴스가 즉시 멈추는 경우는 재지 않았다.

개선 방향:
- 즉시 멈추는 경우의 영향은 헬스체크 간격과 실패 횟수(15초, 2회)에 달려 있다. 간격을 10초로 당기면 빨리 빠지는 대신 헬스체크 요청이 늘어나니 둘을 같이 따져서 정하면 된다.
- 인스턴스 손실을 FIS로 정기적으로 주입해 같은 결과가 유지되는지 보는 게 맞다. Well-Architected도 EC2 인스턴스 손실 같은 장애 주입 실험을 정기적으로 돌리라고 권한다([REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_testing_resiliency_failure_injection_resiliency.html)).
