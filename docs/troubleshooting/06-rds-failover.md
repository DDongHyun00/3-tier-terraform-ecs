# RDS 장애 조치

RDS를 잠시 Multi-AZ로 켜고 강제 장애 조치를 일으켜, DB가 대기 인스턴스로 넘어가는 시간과 그동안 사용자가 받은 응답을 쟀다. 평소에는 비용 때문에 Single-AZ로 둔다. Multi-AZ였다면 그 위험이 얼마나 줄어드는지 숫자로 남기려는 실험이었다.

## 요약

2026-11-05 11:01~11:18 KST에 태스크 2개(가용 영역마다 1개), RDS db.t4g.micro(gp3 20 GB)로 쟀다. 요청은 probe뿐이었다. `/posts`(DB를 거침)와 liveness(DB 없음)를 약 1초 간격으로 보내고, 요청마다 최대 5초를 기다렸다.

| 항목 | 값 |
|---|---|
| Single-AZ에서 Multi-AZ로 변환 | 7분 45초, 그동안 서비스 영향 없음 |
| 장애 조치 (RDS 이벤트 기준) | 43.3초 |
| 사용자 영향 (`/posts`) | 약 44초, 요청 7건이 5초 안에 응답을 못 받음 |
| 장애 조치 완료부터 앱 회복까지 | 1초 미만 |
| 5xx | 0건 |

liveness는 실험 내내 200이었고 태스크 교체는 없었다.

## 재현

1. 코드는 그대로 두고 로컬 apply에서 변수만 바꿔 Multi-AZ를 켠다. RDS 모듈이 `apply_immediately = true`라 변환이 바로 시작된다.

        cd terraform/main
        terraform apply -var multi_az=true

2. 1초 간격으로 `/posts`와 `/actuator/health/liveness`를 기록한다.
3. 강제로 장애 조치를 일으킨다.

        aws rds reboot-db-instance --db-instance-identifier db-3tier-prod --force-failover

4. RDS 이벤트로 시작과 완료 시각을 본다.

        aws rds describe-events --source-type db-instance --source-identifier db-3tier-prod --duration 30

5. 다음 CI apply(변수 기본값 false)나 세션 끝 destroy로 Single-AZ로 돌아간다. 그래서 측정 중에는 main에 인프라 변경을 머지하지 않는다.

## 무슨 일이 있었나

| 시각 (KST) | 일 |
|---|---|
| 11:01:34 | Multi-AZ 변환 시작 |
| 11:09:19 | 변환 완료. 주 DB 2c, 대기 DB 2a |
| 11:13:04 | 마지막 정상 `/posts` (0.08초) |
| 11:13:06 | 장애 조치 시작 |
| 11:13:23 | DB 인스턴스 재시작 |
| 11:13:42 | 마지막 실패 요청 (7번째) |
| 11:13:49 | 장애 조치 완료, 같은 초의 `/posts`가 0.12초에 200 |

실패한 요청 7건은 모두 상태 코드 없이 5초에서 끊겼다. 앱은 DB 연결을 기다리며 요청을 붙잡고 있었고 오류를 돌려주지 않았다. ALB 지표에서도 11:13에 2xx가 31건으로 앞뒤 분(86~88건)보다 줄었고 5xx는 0건이었다. probe가 먼저 끊은 요청은 ALB에 클라이언트 종료로 남아 5xx로도, 응답 시간 지표로도 잡히지 않는다.

장애 조치 뒤 DB 주소는 10.0.20.9(2a의 DB 서브넷)를 가리켰다. 그런데 `describe-db-instances`는 몇 분 뒤에도 주 DB를 2c로 보여 줬다. 어느 쪽이 주 DB인지는 API 속성보다 엔드포인트가 가리키는 IP로 확인하는 게 확실했다.

## 원인

- 장애 조치 시간(43초)과 사용자 영향(44초)이 거의 같았다. 엔드포인트 DNS가 바뀐 직후 HikariCP가 새 주 DB로 연결을 만들어, 앱이 다시 붙는 데 시간이 거의 더 들지 않았다.
- 오류 대신 대기가 났다. [DB 연결 차단](03-db-connection-failure.md)에서는 약 30초 뒤 500이 났는데, 이번에는 장애 구간이 30초를 넘었는데도 5xx가 0건이었다. 다만 probe가 5초에서 끊어서, 30초 넘게 기다린 사용자가 결국 200을 받았는지 500을 받았는지는 이 측정으로 알 수 없다.
- 그래서 5xx 비율 알람으로는 이런 장애를 잡을 수 없다. 오류 응답이 없기 때문이다.

## 조치와 재발 방지

| 상황 | Single-AZ (평소) | Multi-AZ (이번 실험) |
|---|---|---|
| DB 인스턴스 재시작이나 장애 | 재시작이 끝날 때까지 중단 | 약 44초 대기 뒤 회복 |
| DB가 있는 가용 영역 전체 장애 | 복구나 스냅샷 복원까지 중단(수십 분 이상) | 다른 가용 영역으로 넘어감 |
| 시간당 비용 (db.t4g.micro, gp3 20 GB) | 0.03 USD | 약 0.06 USD |

필요할 때만 띄우는 지금 운영에서는 Single-AZ를 유지했다. 24시간 운영으로 바뀌면 시간당 0.03 USD를 더 내고 DB 중단을 약 44초로 줄일 수 있다. probe 기록은 277건 중 실패 7건이었다.

## 배운 점과 개선 방향

배운 점:
- Multi-AZ 장애 조치에서 사용자 영향은 장애 조치 시간과 거의 같은 약 44초였고, 앱은 사람 조치 없이 1초 안에 다시 붙었다. 다만 이 장애는 오류 대신 대기로 나타나서 5xx 비율 알람으로는 잡히지 않는다.
- 어느 쪽이 주 DB인지는 API 속성보다 엔드포인트가 가리키는 IP로 확인하는 게 확실했다.

개선 방향:
- 24시간 운영이라면 Multi-AZ를 켜는 게 맞다. 시간당 0.03 USD를 더 내고 DB가 있는 가용 영역 장애를 견딘다.
- 오류 없이 느려지는 장애는 응답 시간(p95), 요청 수 급감, RDS 이벤트 구독으로 잡으면 된다.
- RDS Proxy를 앱 앞에 두면 DNS 캐시를 거치지 않아 Multi-AZ 장애 조치 시간이 최대 66% 줄고, 앱 연결도 끊기지 않은 채 새 인스턴스로 넘어간다([RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy-planning.html)).
